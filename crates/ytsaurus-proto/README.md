# ytsaurus-proto

Generated protobuf bindings for the YTsaurus RPC proxy.

**Pre-release, published from 0.3.0.** It gives
[`ytsaurus-rpc`](../ytsaurus-rpc) its types; the compatibility contract for
both is [docs/rpc-compatibility.md](../../docs/rpc-compatibility.md).

## The files are not copied

The bindings are generated by `prost-build` from the upstream `.proto` files in
the `third_party/ytsaurus` submodule, not from a vendored copy. A submodule
records an exact upstream commit, the pinning protocol work requires, and keeps
the definitions byte-identical to upstream's, so no copy can drift.

The pin is `stable/25.4` @ `c91fcbe2cd0b9bf8a2fbae078885b9d423f22b62`, chosen
over `main` because the local cluster this was verified against runs that
branch. It moves only when a human moves it.

## The generated Rust is committed, and there is no build script

`cargo package` does not walk into a submodule, so generating at build time
produced a crate that builds from its repository and fails from the registry:
the definitions are not in the tarball, and could not be without the vendored
copy this project does not keep. Committing `src/generated/` is what makes the
crate publishable. Building it needs neither the submodule nor `protoc`, and
its only dependency is `prost`.

Regeneration is a repository task:

```sh
./scripts/init-protos.sh          # once: the submodule, shallow and sparse
cargo xtask generate-protos       # rewrite src/generated/ from it
```

CI runs the same task and fails on a diff, so committed code that has drifted
from the pin is a red build.

`init-protos.sh` checks the submodule out shallow and sparse, about 23 MB
holding `yt/yt_proto/` and little else; a bare `git submodule update --init`
would materialise the whole monorepo. `protoc` need not be on `PATH` to
regenerate either: a vendored binary is used unless `PROTOC` is set, so
`cargo xtask generate-protos` works with nothing but the Rust toolchain, the
standard `scripts/build-worker.sh` is held to.

## What is generated

The transitive import closure of the RPC-proxy API surface: 20 files, listed
explicitly in `xtask/src/main.rs` rather than globbed, so a file appearing
upstream does not silently enlarge what this crate compiles.

`prost` names each module after its protobuf package and writes cross-package
references as `super::`-relative paths, so the module nesting in `lib.rs` must
mirror the package names exactly or the generated code does not resolve. Short
aliases sit on top:

| Alias | Package | Holds |
| --- | --- | --- |
| `misc` | `NYT.NProto` | `TGuid`, `TError` |
| `bus` | `NYT.NBus.NProto` | `THandshake` |
| `rpc` | `NYT.NRpc.NProto` | request and response headers |
| `ytree` | `NYT.NYTree.NProto` | the attribute dictionary errors carry |
| `api` | `NYT.NApi.NRpcProxy.NProto` | all 158 request types and their responses |

## Using them

`required` and `optional` are both visible. These are proto2 files: `prost`
renders a `required` field as a plain value and an `optional` one as an
`Option`. Which a field is cannot be guessed from its name; read the generated
type.

Extensions are not generated. `prost` does not support proto2 extensions, so
`TRequestHeader`'s extension fields, `credentials_ext` at 110 and the rest, are
absent from the generated struct. `ytsaurus-rpc` appends the credentials field
by hand, which is wire-identical because an extension is an ordinary field
with a reserved number.
