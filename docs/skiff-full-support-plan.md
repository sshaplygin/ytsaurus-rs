# Plan: full Skiff support

[`docs/skiff-compatibility.md`](./skiff-compatibility.md) records what is
implemented and which gates are green. This document is the other half: what
"full Skiff support" means measured against the C++ implementation, in the order
the pieces should be built, with the test that closes each one.

"Full" here means the surface `library/cpp/skiff`, `yt/yt/library/skiff_ext`
and `yt/yt/library/formats/skiff_*` expose between them — a job or a client can
be handed any of it by a cluster, so anything short of that is a schema someone
can write and this crate cannot read.

## The audit this plan came from

On 2026-08-16 the crate was compared against the C++ implementation directly,
using `ytsaurus-yson` 0.4.10 — the PyPI wheel whose `load_skiff` / `dump_skiff`
are compiled `library/cpp/skiff`, so the comparison ran the real writer and
parser rather than a third implementation of the format. Six corpora were
generated by the C++ writer, read back by the C++ parser, and then encoded and
decoded by this crate.

Everything compared came out **byte-identical**: `int64`, `uint64`, `boolean`,
`double` and `string32` at their boundaries (including `-0.0` and a non-UTF-8
payload); `variant8<nothing; T>` optionals on both tags; `$sparse_columns` as a
`repeated_variant16` with none, one and several fields set; `$other_columns`
carrying C++-written binary YSON; the `$row_index` / `$range_index` /
`$key_switch` control columns; two table schemas multiplexed by the `Variant16`
prefix; and a `$name` reference resolved through `skiff_schema_registry`.

That is the good news and the reason nothing in Phases 1–3 changes bytes this
crate writes today. The harness itself was not kept — the Go corpus remains the
standing gate, and the cluster fixtures of required test 4 are what will check
the C++ side continuously. What the audit *found* is the numbered work below;
where an item came from the audit rather than from reading upstream, it says so.

Two things constrained the audit and will constrain any repeat of it. The
bindings' Python record layer accepts only `int64`, `uint64`, `boolean`,
`double`, `string32` and `yson32`, and calls `YT_ABORT()` — killing the process
— on anything else, so the narrow and wide integers were unreachable through it.
And `$remaining_row_bytes` and the end-of-stream tag live in
`yt/yt/library/formats/`, not in the serialization library, so the bindings
never emit them.

## Where the work sits

Skiff is three layers, and they fail differently. Keeping them separate is what
lets each phase below have a real gate instead of a vibe.

| Layer | Upstream | Here | What breaks when it is wrong |
| --- | --- | --- | --- |
| Serialization | `library/cpp/skiff` | `ytsaurus-skiff` `wire.rs` | Bytes. A stream is misread or unreadable. |
| Table schema matching | `yt/yt/library/skiff_ext/schema_match.cpp` | partly `ytsaurus-job` `skiff.rs` | Columns. A valid schema is refused, or a column lands in the wrong field. |
| Logical type mapping | `yt/yt/library/formats/skiff_yson_converter.cpp` | absent | Types. A `decimal` or a `list<T>` column cannot be expressed at all. |

## Phase 1 — serialization parity

The smallest phase and the one everything else assumes. Each item is a
divergence the 2026-08-16 C++ run found, in the order of how much it costs to
leave alone.

1. **`uint128` and `uint256`.** Add to `WireType`, `Value` and both codecs.
   `uint128` is sixteen little-endian bytes, `uint256` thirty-two, matching
   `ParseUint128`/`ParseUint256`, which read two and four little-endian `ui64`
   words respectively — low word first. This is not an exotic type: `uuid`
   columns travel as `uint128`, so today the `uuid` path does not exist.
2. **Strict `boolean`.** `TUncheckedSkiffParser::ParseBoolean` throws above 1.
   Decode `0x02` as an error, not as `true`. Note that the Go SDK is lax here
   too, so the Go corpus will not catch a regression — the C++ one must.
3. **The `0xFFFF` end-of-stream tag.** `TSkiffWriter::Close` writes it when
   `EnableEndOfStream` is set. `Decoder::next_row` should read it as a clean
   end of stream rather than as table index 65535, and `Encoder` should grow an
   opt-in `finish_with_end_of_stream`. Keep it opt-in: the tag is a control
   attribute upstream, not an unconditional part of the framing.
4. **Schema validation parity.** Reject a variant with no children, as
   `CreateVariant8Schema` does. Keep this crate's own child-count ceilings —
   C++ has none and a `variant8` with 300 children is simply unreadable.
5. **`int256`/`uint256` value accessors.** The bytes are already carried
   verbatim, which is correct; add the four-`u64` view so a caller does not
   have to know the word order to use one.

**Gate.** Rust round trips and boundary tests for the new types, plus a cluster
fixture that carries a `uuid` column. Note that the Go corpus cannot close any
of these: Go has no `uint128`/`uint256`, no `int128`/`int256` codec, and the
same lax boolean. Phase 5 is about that.

## Phase 2 — table schema matching

This is the layer `schema_match.cpp` owns and the one this crate has only in
part. It should live in `ytsaurus-skiff` as a `TableDescription`, not in
`ytsaurus-job`, because the client's table I/O needs exactly the same rules.

1. **The dense/sparse/other split.** `$other_columns` must be `yson32` and last;
   `$sparse_columns` must be `repeated_variant16` and second-to-last if
   `$other_columns` is present, last otherwise; every remaining root child is a
   dense field and must be named; names must be unique across dense and sparse.
2. **Control columns anywhere in the dense part.** Upstream records the index of
   `$key_switch`, `$row_index`, `$range_index` and `$remaining_row_bytes`
   wherever they sit. `SkiffJobReader` requires a contiguous prefix and must
   stop doing so — that is a schema the cluster accepts and this crate refuses.
3. **`$sparse_columns` as a named map.** Encode and decode the repeated variant
   as `name -> value`, skipping absent and null fields, terminated by `0xFFFF`.
   The wire shape is already verified; what is missing is the naming.
4. **`$other_columns` as a YSON map.** Split it into named values on read and
   gather unnamed columns into it on write. Refusing a row with a column the
   schema does not name and no `$other_columns` field is part of the contract.
5. **`$row_index` / `$range_index` modes.** `variant8<nothing;int64>` is
   `Incremental`: the value is written only when it does not continue the
   previous one, and tag 0 means "one more than the last". The three-child
   form `variant8<nothing;int64;nothing>` is `IncrementalWithError`, where
   tag 2 means the index is unavailable. Only the first is understood today,
   and only as a plain optional.
6. **`$remaining_row_bytes`.** Declared `int32`, written as a `u32` byte count
   followed by the rest of the row — `StartBlob`/`FinishBlob` in the C++
   writer. Needs a two-pass or buffered encode, which is why it is last here.

**Gate.** Cluster fixtures — a job whose input schema carries each shape. The
audit settled the wire shape of items 1, 3 and 4; what no local oracle reaches
is item 5's incremental form or item 6 at all, because both are written by
`yt/yt/library/formats/skiff_writer.cpp` rather than by the Skiff library.

## Phase 3 — YT logical types

`skiff_yson_converter.cpp` is the mapping between a table's logical type and
Skiff. Without it a caller can describe `int64` columns and nothing else.

1. **Composite types.** `optional<T>` → `variant8<nothing; T>`;
   `list<T>` → `repeated_variant8<T>` with tag 0 per item and the `0xFF`
   terminator; `struct` and `tuple` → `tuple`; `variant` → `variant8` or
   `variant16`; `dict<K,V>` → `repeated_variant8<tuple<K,V>>`; `tagged<T>` →
   `T`. Any type at all may instead be carried as `yson32`, which is the
   fallback every converter accepts.
2. **`decimal`.** `int32`, `int64`, `int128` or `int256` by precision, holding
   YT's binary decimal representation.
3. **`uuid`.** `uint128`, with both halves byte-swapped and the high word
   first — `TUuidParser` writes `HostToInet(High)` then `HostToInet(Low)`.
   Easy to get subtly wrong; worth its own vector.
4. **Time-zone types.** `tuple<inner; uint16>`, the second element being the
   time-zone index.
5. **Schema inference.** Build a Skiff format from a YT table schema, the
   equivalent of Go's `InferFormat`, so a caller need not hand-write a Skiff
   schema to read a typed table.

**Gate.** Cluster round trips per type: write with YSON, read as Skiff, compare.
A local corpus cannot settle these — the mapping is only meaningful against a
real table schema.

## Phase 4 — typed rows

1. **Serde `SkiffRow`.** Typed `Scan`/`Write` over the dynamic `Value`, so a
   job declares a struct rather than indexing a tuple. Deliberately last: it
   is ergonomics over a codec that has to be right first.

## Phase 5 — a standing gate against C++

Go stays the always-on reference: it is one `go test`, it needs no wheels, and
it covers the surface most jobs use. What it cannot cover is everything above —
Go has no `int128`/`int256` codec, no `uint128`/`uint256` at all, and no
`$sparse_columns` or `$other_columns` handling anywhere. So a green Go gate says
less about Phases 1–3 than it looks like it does, and something has to say more.
Two candidates, in cost order:

1. **Cluster fixtures.** Already the open gate 4 in the compatibility document,
   and the only thing that can settle Phases 2 and 3 — those layers are only
   meaningful against a real table schema, so no local oracle substitutes.
2. **A compiled C++ harness.** `library/cpp/skiff` is four `.cpp` files, but it
   links Arcadia's `util`, so this means a Docker builder over the pinned
   submodule that writes vectors for the wide types and reads Rust's back.
   Worth building only if Phase 1's types cannot be settled from a cluster.

The 2026-08-16 audit used a third route — the `ytsaurus-yson` wheel, which is
compiled `library/cpp/skiff` — and it is the cheapest way to repeat a one-off
comparison of the six types its Python record layer accepts. It was not kept as
a standing gate.

## Order and why

Phase 1 first: it is small, it is byte-level, and every later phase encodes
through it. Phase 2 next, because it is where a cluster-written schema is most
likely to be refused today — a control column in the wrong place is a real
schema someone will hand us, not a hypothetical. Phase 3 is the largest and
depends on both. Phase 4 is ergonomics and can slip without blocking anything.

Nothing in Phases 1–3 changes the bytes of what this crate writes today; the
2026-08-16 run established that those bytes are already the C++ ones. Every item
is a type, a rule or a framing tag that is currently absent.
